Phase 1 Setup & Prerequisites

Before building the sync pipeline, configure all three tools and set up your project structure. Complete every step here before proceeding.

1.1

Prepare your Figma file

Enable Dev Mode · Organize Variables · Standardize naming

▼

Enable Dev Mode — open your Figma file, click the Figma logo (top-left), and select Enable Dev Mode. This unlocks the Variables API and code inspection.

Organize Variables as tokens. Create variable collections for each category:

  • Color — brand, semantic, and state colors
  • Spacing — base-4 or base-8 scale (4, 8, 12, 16, 24, 32…)
  • Typography — font sizes, weights, line heights
  • Radius — border radius values
  • Shadow — elevation levels

Standardize component naming using the slash convention so Claude can map them to file paths:

// Component naming convention — one entry per line Button/Primary/Default Button/Primary/Hover Button/Primary/Disabled Button/Secondary/Default Button/Secondary/Hover Input/Text/Default Input/Text/Error Input/Text/Focused

Get your Figma credentials. Go to Account Settings → Personal Access Tokens. Create a token with Read scope. Copy your FILE_KEY from the URL:

https://www.figma.com/design/FILE_KEY/Your-File-Name ^^^^^^^^^^^ Copy this part
💡 Tip

Store the FILE_KEY and token in a password manager now. You'll need them in every script in this guide.

1.2

Set up your project folder

Create folders on your computer · Ask a developer to run the install

▼
👋 Designer note

This step is about creating a project folder on your computer — like making a new folder on your Desktop, but with a specific internal structure. You'll do the folder creation yourself (Part A below). Then hand off to your developer for Part B, which installs the technical tools.

Part A — Create the folders (you do this)

This is the folder structure you're building. Think of it like organizing a filing cabinet — each folder has a specific purpose:

Open Terminal (press ⌘ Space, type "Terminal", press Enter). Then paste this block and press Enter:

mkdir -p my-design-system/src/components mkdir -p my-design-system/tokens mkdir -p my-design-system/scripts mkdir -p my-design-system/figma-plugin mkdir -p my-design-system/.github/workflows

You'll see a new folder called my-design-system in whatever directory your Terminal was open in (usually your home folder).

Open Command Prompt (press Win, type "cmd", press Enter). Then paste this block and press Enter:

1.3

Save your secret keys

Create a safe credentials file · Keep it off the internet

▼

Think of this like a keychain — a single file that holds all the passwords and API keys the system needs to connect to Figma, Claude, and GitHub. You create this file once and it never leaves your computer.

What each key does:

  • FIGMA_TOKEN — your personal Figma password that lets the script read your design file (from Step 1.1)
  • FIGMA_FILE_KEY — the ID of your specific Figma file (the string from the URL in Step 1.1)
  • ANTHROPIC_API_KEY — your Claude API key, get it at console.anthropic.com
  • GITHUB_TOKEN — lets the script open Pull Requests on your behalf
  • CHROMATIC_PROJECT_TOKEN — connects Storybook to Chromatic for visual testing

How to create the file:

  • Inside your my-design-system folder, create a new text file and name it exactly .env.local (include the dot at the start)
  • Open it in any text editor (TextEdit on Mac, Notepad on Windows) and paste in this template, replacing the placeholder values with your real keys:
FIGMA_TOKEN=paste-your-figma-token-here FIGMA_FILE_KEY=paste-your-file-key-here ANTHROPIC_API_KEY=paste-your-claude-key-here GITHUB_TOKEN=paste-your-github-token-here CHROMATIC_PROJECT_TOKEN=paste-your-chromatic-token-here
⚠ Important — keep this file private

Never share this file, email it, or upload it to GitHub. It contains private keys that give access to your accounts. Add .env.local to your .gitignore file so Git never picks it up. Ask your developer if you're unsure how to do this.

Phase 2 Figma → Storybook

This phase covers the main push: taking what you've designed in Figma and automatically turning it into working components in Storybook — with Claude doing the translation. Phases 2–4 involve code, so you'll be working alongside a developer. Your role is setting up Figma correctly; the scripts handle the rest.

2.1

Export design tokens from Figma

Pull your design tokens out of Figma so the code can use them

▼

What "tokens" means here: design tokens are your design decisions turned into named values — things like "our primary blue is #0057FF" or "large spacing is 32px". Figma stores these in Variables. This step exports them so the code can use the exact same values.

Your role (in Figma):

  • Make sure all your colors, spacing, and typography are defined as Variables in Figma (not just hardcoded values on shapes)
  • Publish your Figma file after making any token changes (File → Publish styles and variables)

What your developer does: they'll create a script that calls Figma's API to export those Variables as a JSON file, then run a tool called Style Dictionary to convert them into a format the code understands. The script looks like this — you don't need to understand it, just know your developer will put it in the scripts/ folder:

const response = await fetch( `https://api.figma.com/v1/files/${FILE_KEY}/variables/local`, { headers: { 'X-Figma-Token': process.env.FIGMA_TOKEN } } ); const { meta } = await response.json(); fs.writeFileSync('tokens/figma-raw.json', JSON.stringify(meta, null, 2)); console.log(`Exported ${Object.keys(meta.variables).length} variables`);
💡 When to re-run this

Any time you update a color, spacing value, or typography token in Figma, this export needs to re-run before components are re-generated. Your developer can set this up to run automatically every Monday, or you can trigger it manually after a big design change.

2.2

Export your component details from Figma

The script reads your components' names, variants, and visual properties

▼

When you click a component in Figma, you can see its name, variants, colors, and spacing in the right panel. This step automates that — a script reads all of that information for every component at once, so Claude can use it to write accurate code.

What the script reads for each component:

  • Name — e.g. Button/Primary/Default (this becomes the file name in code)
  • Variants — e.g. Default, Hover, Disabled (these become separate stories in Storybook)
  • Description — the description you wrote in Figma appears as documentation in code
  • Visual styles — exact color values, padding, font sizes, corner radius

Your role: make sure every component has a proper slash-style name and a clear description in Figma before running this step. The richer your Figma descriptions, the better Claude's generated code will be.

💡 Writing good component descriptions in Figma

Select a component in Figma → right panel → add a Description. Write it like you'd explain it to a developer: "Primary call-to-action button. Use for the most important action on a screen. Avoid using more than one per page." Claude will use this text as documentation.

2.3

Claude generates the code

Claude reads your Figma spec and writes the React component and Storybook story files

▼

This is the core of the whole workflow. The script packages up everything from the previous two steps — your component's visual specs and your design tokens — and sends it to Claude, which writes the actual code.

What Claude receives:

  • The component's name, variants, and visual properties from Figma
  • Your design token values (colors, spacing, etc.)
  • Instructions to follow your team's coding patterns

What Claude produces for each component:

  • A React component file (.tsx) — the working code version of your design
  • A Storybook story file (.stories.tsx) — shows all variants in Storybook
  • A types file (types.ts) — documents all the props the component accepts

The script your developer writes will look like this — it sends your Figma data to Claude and saves the response as code files:

const Anthropic = require('@anthropic-ai/sdk'); const client = new Anthropic(); async function generateComponent(figmaSpec, tokens) { const msg = await client.messages.create({ model: 'claude-sonnet-4-20250514', max_tokens: 4096, system: `You are a design system engineer. Generate clean, typed React components. Use CSS Modules for styling. Follow the project conventions in the provided context.`, messages: [{ role: 'user', content: `Generate a React component for: ${figmaSpec.name} Figma Spec: ${JSON.stringify(figmaSpec)} Design Tokens: ${JSON.stringify(tokens)} Output: 1) Component .tsx 2) Stories .stories.tsx 3) types.ts` }] }); return msg.content[0].text; }
◈ Improve Claude's output

Ask your developer to add 1–2 existing component files to the script's instructions. This shows Claude your team's coding style, so the generated code will match what you already have — less cleanup work for the developer reviewing the PR.

2.4

Save the code and send it for review

Generated files land in your repo · A Pull Request is opened automatically for the developer to review

▼

After Claude generates the code, the script automatically saves all the files to the right folders and opens a Pull Request on GitHub.

What a Pull Request (PR) is: think of it as a "suggestion box" in GitHub. Instead of the generated code going straight into the live codebase, it sits in a PR so a developer can review it, check it looks right, and approve it before it goes live. This is a safety net.

What you'll see as a designer:

  • A new PR appears in your GitHub repository named something like "feat(design-system): add Button from Figma"
  • The developer reviews it, makes any tweaks, then clicks Merge
  • Once merged, the component appears in Storybook within minutes

The script that does this automatically:

const { Octokit } = require('@octokit/rest'); const octokit = new Octokit({ auth: process.env.GITHUB_TOKEN }); // Write files fs.mkdirSync(`src/components/${name}`, { recursive: true }); fs.writeFileSync(`src/components/${name}/${name}.tsx`, component); fs.writeFileSync(`src/components/${name}/${name}.stories.tsx`, story); fs.writeFileSync(`src/components/${name}/types.ts`, types); // Create PR await octokit.pulls.create({ owner, repo, title: `feat(design-system): add ${name} from Figma`, head: `design-system/${name.toLowerCase()}`, base: 'main', body: `Auto-generated from Figma. Component: ${figmaSpec.key}` });
💡 Designer tip

Once the PR is merged you can open Storybook and check that all your variants look exactly as designed. If something's off, note it and the developer can re-run the generator with an improved prompt.

Phase 3 Storybook → Figma

The reverse direction: when a developer updates a component in code — say they add a new variant or adjust spacing — those changes flow back into Figma automatically. You install a small plugin in Figma, and it updates your components for you whenever the developer merges new code.

3.1

The system watches for code changes

Every time a developer merges new code, the system automatically reads what changed

▼

Your developer doesn't need to remember to trigger the sync. When they merge code changes to GitHub, this step runs automatically in the background. It reads the component files and creates a summary of what they contain — like taking a snapshot of the component's properties.

As a designer, you don't do anything in this step. It's fully automatic. Here's what happens behind the scenes:

  • A GitHub Action triggers as soon as code lands on the main branch
  • A script reads every component file and extracts its variants, props, and style values
  • It saves that summary as a small data file (meta.json) next to each component
  • This snapshot is then compared against the previous version to find what changed

The script that creates these snapshots (your developer sets this up once):

const { Project } = require('ts-morph'); const project = new Project(); project.addSourceFilesAtPaths('src/components/**/*.tsx'); for (const file of project.getSourceFiles()) { const props = file.getInterfaces().map(i => ({ name: i.getName(), properties: i.getProperties().map(p => ({ name: p.getName(), type: p.getType().getText() })) })); fs.writeFileSync( file.getDirectoryPath() + '/meta.json', JSON.stringify(props, null, 2) ); }
3.2

Claude figures out what changed

Claude compares the old and new component, then produces a precise list of what to update in Figma

▼

Once the system has a "before" and "after" snapshot of a component, it sends both to Claude and asks: "What changed, and how should Figma be updated to match?"

Claude responds with a precise action list — not vague descriptions, but specific instructions like "rename this variant from 'large' to 'lg'" or "update this color token reference." This list is what the Figma plugin uses in the next step.

Example of what Claude might return after a developer adds a new button size:

// Claude's output: a list of actions to apply in Figma { "actions": [ { "type": "ADD_VARIANT", "componentSetId": "123", "name": "Size=XL" }, { "type": "UPDATE_TOKEN", "nodeId": "456", "token": "spacing.500" } ]}

The prompt used to ask Claude (your developer configures this once):

"Compare these two versions of a React component. Identify all changes that affect the visual design: - New or removed variant values (e.g. new 'size' prop values) - Renamed props that map to Figma variant properties - Updated design token references in styles - Structural changes (new slots, removed elements) Output JSON with this exact shape: { \"actions\": [ { \"type\": \"UPDATE_VARIANT\", \"nodeId\": \"...\", \"newName\": \"...\" }, { \"type\": \"UPDATE_TOKEN\", \"nodeId\": \"...\", \"token\": \"...\" }, { \"type\": \"ADD_VARIANT\", \"componentSetId\": \"...\", \"name\": \"...\" } ] }"
3.3

The Figma plugin applies updates to your file

You run a small plugin inside Figma — it reads the pending changes and updates your components automatically

▼

This is the step where you, as a designer, take action. Your developer builds a small Figma plugin (stored in the figma-plugin/ folder you created). You install it once and then run it whenever the developer tells you new code has been merged.

How to install the plugin (one-time setup):

  • In Figma, click the Figma logo (top left) → Plugins → Development → Import plugin from manifest
  • Navigate to your my-design-system/figma-plugin/ folder and select the manifest.json file
  • The plugin now appears in your Plugins menu as "Design System Sync"

How to run the sync:

  • After your developer says "I just merged some component changes", open Figma
  • Go to Plugins → Development → Design System Sync
  • The plugin runs, applies all pending changes, and shows a confirmation: "✓ Synced 3 updates from Storybook"
  • Check your components — any renamed variants, updated tokens, or new variants will be there

The plugin code (written once by your developer):

// figma-plugin/code.ts async function applyPendingUpdates() { const res = await fetch('https://your-sync.vercel.app/api/pending'); const { actions } = await res.json(); for (const action of actions) { if (action.type === 'UPDATE_VARIANT') { const node = figma.getNodeById(action.nodeId); if (node) node.name = action.newName; } if (action.type === 'UPDATE_TOKEN') { await applyTokenBinding(action.nodeId, action.token); } } figma.notify(`✓ Synced ${actions.length} updates from Storybook`); await markActionsComplete(actions.map(a => a.id)); } applyPendingUpdates(); // runs automatically when you open the plugin

Phase 5 Ongoing Maintenance

Even with automation, Figma and Storybook can drift apart over time — especially after big design or code changes. These are the tools you and your developer use to catch and fix mismatches, and to handle the inevitable moment when you decide to rename your design tokens.

5.1

Audit drift with Claude

Find every mismatch between Figma and code on demand

▼

"Drift" is when Figma and Storybook get out of sync — a developer changed a button's padding in code but the Figma component wasn't updated, for example. Over time, small drifts add up and the design file stops being a reliable reference.

How to run an audit: ask your developer to run the audit script, or set it to run automatically once a month. Claude compares every Figma component against its code version and produces a report listing every mismatch.

What the report tells you:

  • Breaking — a variant exists in code but is missing from Figma entirely (or vice versa). Needs fixing immediately.
  • Visual — a color, spacing, or font is different between Figma and code. Should be fixed soon.
  • Minor — small inconsistency, low impact. Fix when convenient.

The prompt used to ask Claude (your developer runs this):

"Compare the Figma spec and the React component below. List every mismatch as JSON. For each include: - type: color | spacing | variant | typography | missing - figmaValue: what Figma has - codeValue: what the code has - severity: breaking | visual | minor - suggestedFix: one-sentence description of the fix"
5.2

Token migration

Update all components when Figma variable names change

▼

At some point you'll want to rename your design tokens — maybe you're restructuring your color palette from generic names to semantic ones (e.g. blue-500 → color.brand.primary). This is normally tedious because every component in code references the old name and needs to be updated.

With Claude, this is painless:

  • Rename your Variables in Figma first (the design source of truth)
  • Re-export your tokens (Step 2.1)
  • Give your developer the list of old → new token name mappings
  • They run the migration prompt below — Claude updates every component file automatically

Example: you renamed your spacing tokens from t-shirt sizes to numbers:

"Token names have changed. Migration map: { \"spacing.sm\": \"spacing.200\", \"spacing.md\": \"spacing.400\", \"spacing.lg\": \"spacing.600\" } Update all token references in these component files. Return each file with only token references changed. Do NOT change any component logic or JSX structure."
💡 Tip

Always rename tokens in Figma first, then migrate the code. That way Figma stays the source of truth and the code catches up to it — not the other way around.
